## Findings and limits

**Confirmed visible defect:** first shell `tickets list` uses “undefined reasoning”. The initial estimate20–23% later becomes4% with selected Ballad. A different provisional model may be legitimate, but it is not named and the undefined field is incorrect visible output.

**Observed comprehension friction:** conversation prompts promise own words, but model-switch/plan requests either list models or give generic fallback. `/model forge` works. A task request containing “telemetry off by default” starts unchanged authored work and returns exactly that known finding. I cannot establish implementation intent without source; the evidence proves the extra instruction did not produce the expected review. A deterministic game may intentionally support bounded conversational intents, but it should reveal that boundary and the accepted action.

**Observed strengths:** first useful action is obvious; shipment1 quickly unlocks parallel providers. Reviews clearly distinguish risk from an unresolved finding, name tests and scope, and warn that approval escapes a known defect. Revision changes evidence concretely. Cache recovery offers a product scope choice and an orchestration choice. Occupancy changes the default workflow and is explained. The quota pane gives continuously usable pool comparison. No tool waits forced me idle.

**Structural analysis limited to this run:** the generic APP-118 and PLAT-77 sequence was start -> blockedreview -> revise -> passedreview -> approve; once learned, the second repeated it without a new choice. Model/risk reduction did not remove the cache's known finding, so the review gate dominates numeric risk for these jobs. Cache repair was richer because scope and occupancy changed the preferred next action. This is not proof of a universal dominant strategy or exhaustive rules analysis.

**Taste judgment under brief:** I would continue for a newly introduced capability, as with cache workflows/panes, but would stop if subsequent jobs mostly repeat generic revise then approve. Four ships plus dashboard is my observed stopping point for this bounded explorer run, not a human retention estimate. Dashboard is optional, readable and inexpensive here; I would prefer it reveal actionable blocked work once busy, but busy dashboard coverage is absent, so no recommendation is based on an assumed omission.

**Review choice understanding:** before approval1 I understood pass/ship, revise/another agent pass, escalate/+4health/-3trust/nodeliveryreward. I could not predict generic revision quota/duration. Before cache repair I could predict scope reward, timing, helper occupancy, setup quota and context. Escalation did not explain whether it preserves the ticket as ready work or resolves it without shipping; I did not test it.

## Ready-for-agent improvement hypotheses

### 1. P1 — Make acceptance of added task constraints explicit

Classification: observed friction with a likely interaction-contract defect; implementation intent unverified.

Reproduction: fresh Cedar -> ship APP-101 -> launch Forge -> `/model forge` -> `Please take APP-118 with telemetry off by default` -> inspect review. Start says ticket exactly as written; review says generated default enabled unless brief says otherwise. The player attempted the exact correction the warning later demands.

Scope: deterministic conversation intent handling and its response for authored acceptance constraints, starting with APP-118. Support a small explicit domain of acceptance choices or clearly identify the unaccepted clause and give the command/control that will clarify the brief. Echo accepted action and accepted constraints before work. No AI service or unrestricted prompt semantics.

Observable acceptance: the same sentence either applies a visibly named disabled-default constraint with corresponding review evidence, or produces an explicit “I can start this ticket, but that default constraint was not applied; use …” response without pretending the entire request was fulfilled. A focused scenario test verifies both the supported variant and unsupported added constraints. Run the same browser route.

Risks: making prevention automatic could erase the interesting review recovery lesson; broad fuzzy parsing might accept constraints incorrectly or route compound prompts inconsistently. Keep authored outcomes deterministic, preserve save compatibility, and compare first-session comprehension rather than adding text by default.

### 2. P2 — Give useful feedback for natural-language model and plan controls

Classification: observed interaction friction, distinct from task-constraint semantics.

Reproduction: on Forge, `Use a balanced model and plan APP-118 with telemetry off by default` only lists models; `Switch to forge` yields generic next-ticket reply; `Please plan APP-118 with telemetry off by default` does not plan. `/help` then `/model forge` succeeds; terminal `/help` reveals `/permissions plan`.

Scope: conversation session-control aliases or bounded fallback guidance. Recognize named model selection and plain “plan this/next ticket”, or answer with an exact contextual suggestion. For compound prompts, identify which one action was accepted and which remains pending. Keep exact CLI available.

Observable acceptance: “Switch to forge” either visibly changes the active model or returns a single useful `/model forge` suggestion. “Please plan APP-118” either enables the explained 5quota next-assignment plan or points directly to `/permissions plan` with the cost. No generic work-on-next-ticket response to an identified control request. Focused parsing tests plus a browser retest.

Risks: provider/model share the word Forge; aliases must not relaunch providers or unexpectedly start tasks. Plan-mode persistence must be explained accurately. Avoid implementing every possible paraphrase.

### 3. P2 — Remove undefined and unnamed pre-launch risk assumptions

Classification: confirmed visible output defect plus estimate-disclosure observation.

Reproduction: new shell before launching agent -> `tickets list`; footer shows “selected model and undefined reasoning”; APP-101 estimate20–23%, then Anthill `Tell me about APP-101` reports selected Ballad medium4–4%.

Scope: shell backlog estimate labeling/default state. Either omit model-dependent estimates until a provider is selected or name provisional provider/model/reasoning and explain how to select one. Retain baseline risk.

Observable acceptance: no `undefined` or unnamed selected model in fresh shell output; player can explain why shell and agent estimates differ. Focused formatter/default-state test; actual fresh-browser command verification.

Risks: removing all estimates can reduce useful early comparison; giving a hidden default undue authority can bias selection. Avoid changing deterministic risk math just to make numbers match.

### 4. P2 — Expose generic revision cost and expected resolution before acting

Classification: observed information gap; cache review provides an existing stronger comparison.

Reproduction: APP-118 or PLAT-77 blocked review lists revise as “resolve finding; another agent pass”, without time/quota/context cost. After `Please revise …`, only narrower-second-pass confirmation appears. PERF-204 review instead previews 3/5s, setup quota, helper requirement and context.

Scope: general revision preview in existing review output and start confirmation. Name the specific finding being addressed and predicted costs using current state. Do not add a separate confirmation screen or extra required command.

Observable acceptance: before generic revise, a player can state which visible warning it addresses, approximate work duration, provider/pool charged and any upfront cost. Start confirmation matches preview; revised review cites resolved evidence. Focused deterministic preview tests with current quota/occupancy; browser replay of APP-118 and PLAT-77.

Risks: overlong previews can bury tests and gate guidance; don't falsely promise that all risks disappear. This may improve informed agency without solving repeated generic recovery; compare added information against transcript length.

### 5. P2 — Turn capability unlocks and dashboard purchase into immediate discoverable actions

Classification: observed discoverability friction / design hypothesis.

Reproduction: shipment3 unlock message mentions slot3, `watch agents`, isolation but no pane example. `mux` later reveals `pane split quota`. `upgrades buy terminal-dashboard` approves dedicated tab but does not open it or name command; I guessed `dashboard` and it worked. `upgrades list` calls cost14 but does not show that currency is trust or the current balance.

Scope: short capability event/suggestion output. Shipment3 offers one contextual pane command; dashboard purchase offers/openable `dashboard` command; upgrades list names trust and current balance. Avoid auto-opening paid dashboard if it disrupts active terminal work.

Observable acceptance: a fresh explorer reaches a useful pane and purchased dashboard by visible suggestions without guessing or rereading the full help. Purchase visibly reports trust14 and resulting balance. Existing exact commands still work; browser verify occupied-work and idle unlock states.

Risks: automatic pane/window changes can interrupt ongoing work; duplicate watch tabs can create clutter. A concise inline command is preferable to forced navigation. A discovery improvement does not prove the new view improves strategy.
